# 게임 클라이언트 — 소스 코드

Win32 / Direct2D 기반 게임 구현물입니다. **레퍼런스 코드 없이 직접 작성했습니다.**

## Direct2D 렌더링 — 구조를 단계적으로 분리해 나간 과정

세 폴더가 같은 문제를 다루되, 코드를 어떻게 나눌지가 단계마다 다릅니다.

| 단계 | 경로 | 구조 |
|---|---|---|
| 1 | `Direct2D_01_Practice/` | **단일 파일 · 전역 변수** — 렌더 타깃과 비트맵을 전역으로 두고 `Render()`를 `WM_PAINT`에서 호출 (1개 파일) |
| 2 | `Direct2D_02_ExSprite/` | **클래스 분리** — `CDevice`(장치 생성) · `CRenderer`(그리기) · `CSprite`(시트 분할) · `CWIC`(이미지 디코딩) · `CWindow` (11개 파일) |
| 3 | `Direct2D_03_MoveSprite/` | **역할 세분화** — 2단계 구성에 `Player`(입력·상태)를 분리해 그리는 쪽과 움직이는 쪽을 나눔 (13개 파일) |

1단계 코드에서는 `g_pRenderTarget`, `g_pBitmap` 같은 전역 핸들을 직접 관리하고 해제 시점도 손으로 맞춰야 했습니다. 2·3단계에서는 장치 생성과 해제를 클래스 생명주기에 맡기고, 그리기·이미지 로딩·객체 상태를 각각 다른 파일로 떼어냈습니다. 세 폴더를 함께 두는 이유는, 무엇이 불편해서 나눴는지가 코드로 남아 있기 때문입니다.

## 게임 로직

| 경로 | 내용 |
|---|---|
| `Gomoku/` | 오목 승패 판정 — 방금 놓인 좌표를 기준으로 8방향을 탐색 |
| `MetalSlug/` | 스프라이트 게임 — `Game` 클래스로 게임 로직과 윈도우 코드 분리 |
| `SlidingPuzzle/` | 숫자 퍼즐 — 격자 상태 관리와 이동 규칙 |
| `Bitmap/` | `CDib` — 비트맵 파일을 직접 파싱해 화면에 출력 |

**오목 판정 구조** — `CheckOmok(row, col, dRow, dCol, board)`는 방향 벡터를 받아 같은 돌이 몇 개 이어지는지를 셉니다. `WhoISWin()`은 이를 4개 방향에 대해 정방향·역방향으로 두 번 호출하고, 양쪽 개수에 방금 놓은 돌 하나를 더해 5 이상이면 승리로 판정합니다. 판 전체를 훑지 않고 마지막에 놓인 한 점에서만 뻗어 나가면 되는데, 새로 만들어진 5목이라면 반드시 그 돌을 지나기 때문입니다.

## 자료구조 직접 구현

| 경로 | 내용 |
|---|---|
| `Snake/` | 콘솔 스네이크 게임 + **STL 없이 직접 만든 컨테이너** — `String`(214줄) · `Vector` · `List` · `linked_list`(320줄) · `SingleTon` |

뱀의 몸통처럼 길이가 계속 바뀌는 자료를 다루면서, 컨테이너를 가져다 쓰는 대신 직접 만들어 동작을 확인했습니다. 재할당이 언제 일어나는지, 그때 기존 원소를 가리키던 포인터가 왜 무효가 되는지는 직접 구현해 봐야 손에 잡히는 부분이었습니다.

> **빌드 안내** — Win32 데스크톱 애플리케이션입니다. 프로젝트 파일(`.sln`/`.vcxproj`)과 리소스(이미지·아이콘)는 저장소에서 제외했으며, 코드 열람 목적입니다.
